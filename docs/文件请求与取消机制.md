# 文件请求发起与取消机制

## 概述

Rivet 使用 **requestId + AbortController** 机制实现文件操作的发起、追踪和取消。

### 核心设计

1. **requestId**：由 UI 层生成唯一 UUID，用于追踪和取消
2. **AbortController**：Web 标准 API，用于中断进行中的请求
3. **ProtocolResponse**：联合类型响应格式，包含 requestId 和操作结果
4. **防重入**：避免快速切换目录时，过时响应覆盖最新状态
5. **void 忽略**：异步调用使用 `void` 明确表示不关心返回结果

## 请求取消机制

### 取消流程

```
渲染进程生成 requestId
    ↓
渲染进程调用 void window.electronAPI.protocol.cancel(requestId)
    ↓
protocol.handler.ts → protocolService.cancel(requestId)
    ↓
ProtocolService.cancel(requestId)
    ├─ 从 activeRequests 获取 AbortController
    ├─ 调用 controller.abort()
    └─ 从 activeRequests 删除记录
    ↓
协议层检测到 abort 信号
    ↓
抛出 AbortError
    ↓
executeWithRequest 捕获异常，返回错误响应
```

### 取消触发场景

| 场景         | 说明                                 |
| ------------ | ------------------------------------ |
| 快速切换目录 | 用户快速点击不同目录，先前请求被取消 |
| 会话切换     | 切换到其他会话时，取消当前会话的请求 |
| 会话断开     | 连接断开时，自动取消所有进行中的请求 |

### void 忽略返回值

使用 `void` 明确表示不关心异步调用的返回值：

```typescript
// 取消请求时不关心结果
void window.electronAPI.protocol.cancel(oldRequestId)
```

## 防重入机制

当用户快速切换目录时，可能出现：旧请求响应晚于新请求到达的情况。

### SessionStore 中的防重入

[session.store.ts](../src/renderer/features/session/stores/session.store.ts) 中的 `currentListRequestId` 状态：

```typescript
interface SessionStore {
  currentListRequestId: string | null // 当前正在等待的请求 ID
}
```

**处理逻辑**：

```
新请求发起时：
    ├─ 生成 requestId：window.electronAPI.utils.generateUuid()
    ├─ 取消旧请求：void window.electronAPI.protocol.cancel(oldRequestId)
    ├─ 更新状态：currentListRequestId = requestId
    └─ 设置 loading = true

响应到达时：
    ├─ 检查 response.requestId === currentListRequestId
    ├─ 不相等 → 丢弃响应（旧请求的响应）
    └─ 相等 → 处理响应，更新文件列表
```

## 超时机制

### 超时常量

[timeouts.ts](../src/shared/constants/timeouts.ts)：

| 操作   | 超时时间 |
| ------ | -------- |
| LIST   | 30 秒    |
| MKDIR  | 10 秒    |
| RENAME | 10 秒    |
| DELETE | 30 秒    |
| COPY   | 60 秒    |
| MOVE   | 30 秒    |

### 超时处理流程

```
请求发起 → 设置超时定时器
    ↓
超时触发 → controller.abort()
    ↓
抛出 AbortError
    ↓
返回错误响应：
{
  requestId: "xxx",
  success: false,
  error: { code: "REQUEST_ABORTED", message: "Request was cancelled or timed out" }
}
```

## ProtocolResponse 结构

[protocol-request.ts](../src/shared/types/protocol-request.ts)：

```typescript
// 成功响应
interface ProtocolSuccessResponse<T> {
  requestId: string
  success: true
  value: T
  error: undefined
}

// 错误响应
interface ProtocolErrorResponse {
  requestId: string
  success: false
  value: undefined
  error: ErrorInfo
}

// 联合类型
type ProtocolResponse<T> = ProtocolSuccessResponse<T> | ProtocolErrorResponse
```

**判断响应状态**：

```typescript
import { isProtocolResponseErr, isProtocolResponseOk } from '@shared/types/index.js'

if (isProtocolResponseErr(response)) {
  // response.error 是 ErrorInfo 类型
  // response.value 是 undefined
} else {
  // response.value 是 T 类型
  // response.error 是 undefined
}
```

## 其他文件操作

以下操作的机制与 list **完全相同**：

| 操作   | 方法       | 说明                                      |
| ------ | ---------- | ----------------------------------------- |
| mkdir  | 创建目录   | 同样使用 executeWithRequest + AbortSignal |
| rename | 重命名文件 | 同上                                      |
| delete | 删除文件   | 同上                                      |
| copy   | 复制文件   | 同上                                      |
| move   | 移动文件   | 同上                                      |

**差异仅在于**：

- 调用的协议实现方法不同（SftpProtocol.mkdirImpl vs SftpProtocol.listImpl）
- 超时时间不同（LIST 30秒 vs MKDIR 10秒）

## 总结

✅ **UI 层生成 requestId**：发起请求前即可获得 requestId，支持立即取消
✅ **统一请求管理**：所有文件操作通过 executeWithRequest 统一处理
✅ **请求可追踪**：requestId 贯穿整个请求生命周期
✅ **可取消**：通过 AbortController 实现请求中断
✅ **防重入**：避免过时响应覆盖最新状态
✅ **超时保护**：防止请求无限等待
✅ **类型安全**：ProtocolResponse 使用联合类型，TypeScript 自动推断
✅ **明确意图**：使用 `void` 明确表示不关心返回结果
